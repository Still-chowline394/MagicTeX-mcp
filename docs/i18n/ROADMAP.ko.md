## 완료: MagicTeX 자체 상태의 안전한 동시 사용

프로젝트의 `magictex` MCP 서버에 연결하는 Claude Code 세션은 각각 **자신만의 독립된 프로세스**를 띄웁니다(stdio MCP = 클라이언트당 자식 프로세스 하나) — 즉 같은 논문을 다루는 두 세션은 메모리 상태를 전혀 공유하지 않습니다. 지금까지는 둘이 같은 디스크 파일을 두고 경쟁하는 걸 막을 방법이 없었습니다.

- **크로스 프로세스 락**(`src/lock.ts`) — `.latex-preview/.lock` 위치의 배타적 락 파일. 원자적 생성(`O_EXCL`)으로 획득하며, 실효 복구 기능이 있음(소유 프로세스가 죽었거나 락이 30초 넘게 오래됐으면 자동으로 정리되어, 크래시한 agent가 다른 agent를 영구히 막지 못함).
- **보호 대상**: `add_comment` / `resolve_comment` / `reply_to_comment` / 거절 후 삭제(`commentsStore.ts`의 모든 변경 함수)와 체크포인트 생성/복원(`createCheckpoint`, `restoreCheckpoint`, `restoreFile`) — 이제 각각의 전체 읽기-수정-쓰기 과정이 배타 제어 없이 이뤄지던 것과 달리 **하나의 크로스 프로세스 임계 구역**으로 실행됩니다.
- **원자적 쓰기** — `comments.json`은 임시 파일에 쓴 뒤 대상 파일에 덮어 이름을 바꾸므로, 동시에 읽는 쪽(읽기 자체는 락이 필요 없음 — 블록될 이유가 없으므로)이 절반만 쓰인 파일을 보는 일이 없습니다.
- 검증됨: 진짜로 독립된 두 OS 프로세스가 `add_comment`를 동시에 연타해도 쓰기가 하나도 유실되지 않음; 죽은 프로세스가 남긴 락은 타임아웃을 기다리지 않고 100ms 이내에 정리됨.

**이 방식이 커버하지 못하는 것**: 두 agent가 일반 파일 편집 도구로 **같은** `.tex` 파일을 동시에 편집하는 경우. 이 쓰기는 우리 MCP 서버를 전혀 거치지 않고 디스크에 직접 이뤄지므로, 우리가 추가한 락으로는 손댈 수 없습니다. 지금 바로 두 agent를 실험해보고 싶다면, 아래 마일스톤이 나올 때까지 **서로 겹치지 않는 파일**만 다루게 하세요(하나는 `intro.tex`만, 다른 하나는 `related-work.tex`만).

## 다음 마일스톤: 진짜 multi-agent(병렬 편집)

reviewer, author, defender agent가 같은 논문을 **동시에**, 공유 락을 통해 순서를 기다리는 게 아니라 실제로 병렬로 편집.

- **방향**: git worktree/브랜치를 통한 agent별 격리. 각 agent가 자기 worktree에서 독립적으로 작업·컴파일하고, 조정 단계(사람이 검토하거나 전담 integrator agent)가 브랜치를 프로젝트에 다시 병합.
- **필요한 것**: worktree 생명주기 관리(agent 실행마다 생성, 병합/폐기 후 정리), 병합 충돌 UX(문단 단위 충돌은 git만의 문제가 아니라 콘텐츠 문제이기도 해서 어떻게 보여줄지 고민이 필요), 아마 브랜치별 PDF 미리보기나 "병합 후 재컴파일" 단계, 그리고 병렬 agent 실행을 시작·추적할 새 MCP 도구/명령.
- **아직 시작 안 함.** 이 마일스톤이 나오든 안 나오든 위의 락은 실질적인 안전망입니다 — "같은 프로젝트에 Claude Code 세션을 하나 더 열어뒀다"는 상황을 오늘부터 조용한 데이터 유실 함정이 아니라 안전한 상태로 만들어주는 게 바로 이 락입니다.
