## 実装済み:MagicTeX 自身の状態を安全に並行利用

プロジェクトの `magictex` MCP サーバーに接続する Claude Code セッションはそれぞれ**独立したプロセス**を起動します(stdio MCP はクライアントごとに子プロセス 1 つ)——つまり同じ論文を扱う 2 つのセッションはメモリ上の状態を一切共有しません。これまで、両者が同じディスク上のファイルを取り合うのを防ぐ仕組みは何もありませんでした。

- **クロスプロセスロック**(`src/lock.ts`)——`.latex-preview/.lock` に置かれる排他ロックファイル。アトミックな作成(`O_EXCL`)で取得し、失効時の回復機能付き(所有者プロセスが死んでいるか、ロックが 30 秒以上古い場合は自動でクリアされるので、クラッシュした agent が他を永久にブロックすることはありません)。
- **保護される範囲**:`add_comment` / `resolve_comment` / `reply_to_comment` / 却下して削除(`commentsStore.ts` のすべての変更処理)と、チェックポイントの作成・復元(`createCheckpoint`、`restoreCheckpoint`、`restoreFile`)——いずれも「読み込み→変更→書き込み」の一連の流れが**ひとつのクロスプロセス・クリティカルセクション**として実行されるようになりました(以前は排他制御なしの読み込み→変更→書き込みでした)。
- **アトミックな書き込み**——`comments.json` は一時ファイルに書いてから対象ファイルにリネームするので、並行して読む側(読み込み自体はロック不要——ブロックする必要がないため)が書きかけの状態を目にすることはありません。
- 検証済み:2 つの本当に独立した OS プロセスが `add_comment` を同時に連打しても書き込みは一件も失われない。クラッシュしたプロセスが残したロックは、タイムアウトを待たずに 100ms 未満でクリアされる。

**これでカバーできないこと**:2 つの agent が通常のファイル編集ツールで**同じ** `.tex` ファイルを同時に編集するケース。この書き込みは MCP サーバーを一切経由せず直接ディスクに行われるため、私たちが追加したロックでは制御できません。今すぐ 2 つの agent を試したいなら、下のマイルストーンが出るまでは**重ならないファイル**だけを触らせてください(一方は `intro.tex` だけ、もう一方は `related-work.tex` だけ、など)。

## 次のマイルストーン:本当の multi-agent(並列編集)

reviewer・author・defender の各 agent が同じ論文を**同時に**、実際に並行して文章を編集する——共有ロックを介して順番待ちするだけではなく。

- **方向性**:git worktree/ブランチによる agent ごとの分離。各 agent は自分の worktree で独立して作業・コンパイルし、統合ステップ(人間によるレビュー、または専用の integrator agent)でブランチをプロジェクトにマージし直す。
- **必要なもの**:worktree のライフサイクル管理(agent 実行ごとに作成、マージ/破棄後にクリーンアップ)、マージ競合の UX(段落レベルの競合は git だけの問題ではなくコンテンツの問題でもあり、どう見せるかはよく考える必要がある)、おそらくブランチごとの PDF プレビューか「マージしてから再コンパイル」というステップ、そして並列 agent 実行を起動・追跡するための新しい MCP ツール/コマンド。
- **未着手。** このマイルストーンが実現するかどうかに関わらず、上記のロックは実質的な安全網です——「同じプロジェクトで Claude Code のセッションをもう一つ開いたままにしていた」という状況を、静かなデータ損失の罠から今日から安全なものに変えているのはこのロックです。
